## Overall assessment

JSM Studio is becoming easier to scan, but a complicated profile is still difficult to understand and edit confidently. The strongest remaining problems are **incorrect availability information, unclear editing context, and relationships that are visible only after visiting several different pages**.

The recent physical grouping, blue accents, larger glyphs, and persistent layer selector are useful improvements. They should stay. The next pass should make the UI answer these questions reliably:

1. What does this control do in this context?
2. Where else is it used?
3. Where did this value come from, and what will this edit change?
4. What is currently saved, applied, and being edited?

Compared with the supplied Steam Input examples, our Overview has moved closer to the right structure. Our layer editing still requires a more technical mental model. There is also a material behavior difference: Steam supports combining layers, while the current JSM implementation selects one effective layer.

Screens were examined at **1440×900** and **1024×720**. These are task walkthroughs and an expert usability assessment, not a user study. Controller timing, hardware output, installed-app integration, and a live Steam client were not tested.

Steam's visual comparison uses the screenshots supplied in this task. That document supports multiple active layers and assigning layer actions through an input's binding menu; its pictured configurator is not evidence of the latest Steam client layout.

## Prioritized findings

**P1:** fix before further visual polish; affects correctness or confidence.  
**P2:** next usability pass; reduces searching, interpretation, and navigation effort.

### 1. P1 — “Unbound” does not mean available

**Observed:** In Wardogs, Wardogs Menu, and Cyberpunk, the right grip enables gyro through `GYRO_ON = MISC5`. Overview initially omits it. Show Unbound Inputs reveals a row saying **Unbound**. Buttons shows `GYRO_ON` for the same control.

Cyberpunk also assigns analog virtual triggers through `ZL_MODE = X_LT` and `ZR_MODE = X_RT`. Overview labels LT and RT Unbound; Triggers correctly shows the analog-output mode above separate unbound digital rows.

This directly defeats the original purpose of finding spare inputs. Adding a new action there can unintentionally combine it with an existing function.

**Change:** build one shared account of input use, covering ordinary bindings, analog output, gyro conditions, modeshifts, chords, and layer actions. Say **No direct binding · Enables gyro** where appropriate. Reserve **Available** for a defined context in which no relevant uses were found; provide a separate across-layers usage view.

**Acceptance:** both pages and the diagram agree about MISC5 and the analog triggers in Cyberpunk. Selecting the usage explanation opens the relevant setting.

### 2. P1 — Discard restores the edit later

**Reproduced:** change Wardogs' Y output from F to P → select Cyberpunk → choose **Discard and switch** → reopen Wardogs. Y still shows P and the profile is dirty. The mock saved profile remains F, with no save or apply calls.

The confirmation explicitly promises that switching will discard the changes. Returning the draft violates that promise and makes later Save/Apply risky to reason about.

**Change:** make Discard remove the draft and restore the saved content. If retaining drafts is desirable, offer a separately named **Keep draft and switch** action.

**Acceptance:** that exact sequence returns F, with no pending changes, after Discard. Keep draft, if offered, returns P.

[Confirmation](C:/Users/luker/code/JSM_Studio/tmp/ui-audit-2026-09-17/Discard-prompt.png) · [Returned draft](C:/Users/luker/code/JSM_Studio/tmp/ui-audit-2026-09-17/Discard-returned-draft.png)

### 3. P1 — Creating a layer leaves the wrong editing context selected

**Reproduced:** starting on Default, create “Vehicles persistent.” The Editing layer selector still reads Default. An immediately subsequent binding edit would therefore affect Default, not the layer just created.

The migration checkbox also starts selected. With a hold input assigned, creating a layer may move its existing modeshifts while leaving the user looking at Default. This second behavior is source-confirmed; the creation probe used an unassigned hold input.

**Change:** create → select the new layer → show a short description of what it inherits. Before migration, show which groups and how many bindings/settings will move.

**Acceptance:** creating Vehicles makes Vehicles the current editing layer. Editing Y there creates its override while Default's Y remains unchanged.

[After creation](C:/Users/luker/code/JSM_Studio/tmp/ui-audit-2026-09-17/Layers-after-create.png)

### 4. P1 — Layers do not yet provide Steam's combination behavior

**Source-confirmed:** there is one persistent layer slot. Applying another replaces it. A held layer is chosen ahead of that persistent layer; if several are held, the first configured one wins.

For example, applying Vehicles then holding Comms produces **Default + Comms** while held. Vehicles remains remembered but its overrides are temporarily absent. Releasing Comms returns to Vehicles.

Steam supports multiple applied layers with ordering determining conflicts. Our current behavior can surprise someone who expects independent Comms and vehicle controls to coexist. [Valve's layer semantics](https://partner.steamgames.com/doc/features/steam_controller/action_set_layers?l=english).

**Change:** given the requested Steam-like behavior, support an ordered collection of active layers and show conflicts clearly. Distinguish **Editing: Comms** from **Active: Vehicles + Comms**. Preserve the order and underlying held actions during transitions.

**Acceptance:** non-conflicting Vehicles bindings remain active while Comms is held; overlapping bindings use a documented order; removing one layer preserves the others. This requires runtime tests and a controller playtest, beyond this UI audit.

### 5. P1 — Layer actions are separate from ordinary binding editing

**Observed and source-confirmed:** Hold/Apply/Remove are configured in Manage layers, not offered in the ordinary output picker. The badge on a paddle describes its layer action but is not an editable binding or navigation link.

The activation menu includes physical pad-click inputs, but excludes **LT/RT and numbered pad regions**. The supplied Steam Precision example uses LT to hold a layer, so that workflow cannot currently be recreated through this menu.

**Change:** make **Hold layer**, **Apply layer**, and **Remove layer** normal binding choices. Display the named destination directly in the binding row and let it open the layer. Use the supported input model to populate activation choices, with clear semantics for analog thresholds and touch inputs.

**Acceptance:** from LT's editor, assign Hold Precision; from a paddle, edit or remove its layer action without searching through a separate manager. Existing keyboard/mouse actions on the same input remain visible.

### 6. P2 — Inheritance and change indicators are too coarse

**Observed:** selected-layer button cards can show Default/Override, but gyro fields do not identify their origin. Returning an override to inheritance requires opening raw keys in Manage layers. Wardogs also inherits from FPS Template, introducing a second origin that the user needs to understand.

After creating an otherwise empty layer, the untouched Gyro panel displays its own Unsaved changes badge. The global pending-change flag is passed to that panel, so this badge does not identify a gyro-specific edit.

**Change:** show per-value origin, such as **Default → FPS Template**, and put **Use Default** alongside the changed field or binding. A local badge should describe local changes; the header can retain the whole-profile status. Distinguish resetting a local override from deliberately assigning None.

**Acceptance:** changing only a face binding does not mark Gyro as edited. A gyro value can reveal its source and restore inheritance in place. Extend the existing [TODO-1](C:/Users/luker/code/JSM_Studio/docs/TODO.md:24) rather than creating a parallel inheritance mechanism.

[Inherited Gyro panel](C:/Users/luker/code/JSM_Studio/tmp/ui-audit-2026-09-17/Layers-inherited-gyro.png)

### 7. P2 — Overview still conceals the behavior that makes profiles complicated

**Observed:** Wardogs shows “Modeshift trigger · 13 bindings/settings” for Utility, generic counts for other modifiers, and the raw expression `!M\ !M/` for Tactical map. The right-pad click's shift changes its behavior, but Overview does not explain that change. Gyro has a navigation tile, with no behavior summary.

The usage badges expose more information through tooltips, but do not offer a controller-accessible list of affected inputs. Someone asking “everything R4 changes” still has to inspect multiple pages.

**Change:** make summaries describe effects: **Hold right grip → Enable gyro**, **Hold pad click → 4-way button pad**, **Hold R4 → Comms**. Give each modifier a selectable **Show affected inputs** disclosure. Add compact gyro output/activation information. Offer **All bindings / Overrides / Available / Uses this modifier**, plus search across action names and outputs.

This is the useful principle in the supplied Steam screenshots: related behavior is named next to the relevant control. Avoid displaying every technical setting in the overview row.

**Also reproduced:** in a synthetic rectangular 3×3 pad, Show Unbound exposes only the four already-assigned cells. Derive available cells from the configured geometry. Untouched Wardogs uses a four-way pad, so this is not a claim that Wardogs itself has five missing regions.

[Wardogs Overview](C:/Users/luker/code/JSM_Studio/tmp/ui-audit-2026-09-17/Wardogs-overview.png) · [Grid availability](C:/Users/luker/code/JSM_Studio/tmp/ui-audit-2026-09-17/Grid-availability-overview.png)

### 8. P2 — Too much space is spent getting to the binding

**Observed at 1440×900:** Wardogs Overview has about 1,926 pixels of scrollable content in a 719-pixel content viewport. The first face/stick rows only start near the bottom of the initial screen. Expanding Y uses a substantial portion of the page for one keyboard output; the relevant modeshift group begins below it.

**Observed at 1024×720:** wrapping navigation, utility controls, and the layer strip consume roughly the first 390 pixels. A vertical section list then pushes the first binding below the viewport. This is a real regression in usefulness when narrowing the window.

**Change:** use a compact navigation drawer at this width, a short section switcher, and a compact binding row with optional expanded settings. Keep profile/layer context visible. Let Overview reduce the controller illustration's space or collapse it while preserving logical groups and section jumps.

Complex profiles will need scrolling. The target is to reveal useful actions early and make returning to a group predictable, not to compress every mapping onto one screen.

[Expanded Y](C:/Users/luker/code/JSM_Studio/tmp/ui-audit-2026-09-17/Wardogs-face-shift.png) · [Narrow window](C:/Users/luker/code/JSM_Studio/tmp/ui-audit-2026-09-17/Layers-1024-buttons.png)

### 9. P2 — Back closes controls but does not retrace navigation

**Reproduced with keyboard:** Overview → Y correctly opens/focuses the Y editor. Two Escape presses leave the user on Buttons. There is no page-history return in this route; the footer nevertheless advertises Back.

**Change:** maintain a small navigation history: close the current popup/detail first, then return to the originating page, layer, scroll position, and focused input. Keep the physical controller's Back action consistent with this behavior.

**Acceptance:** Overview → Comms → Y → Back returns predictably to the same Comms Overview position. Verify with the controller as well as keyboard after implementation.

### 10. P2 — Icon accuracy and diagram correspondence need one shared definition

The larger solid glyphs are easier to read. Remaining issues go beyond their style:

- Steam trigger labels differ between diagram (L2/R2) and binding glyphs (LT/RT).
- Grip list entries use MISC5/MISC6, while diagram highlight checks use GRIP_R/GRIP_L. Pad highlight checks similarly use different identifiers. This breaks reliable correspondence between an input row and its physical location.
- Source inspection shows the non-Steam diagram uses DualSense geometry even for Xbox/Nintendo families. This was not separately rendered in the walkthrough.
- Configured inputs from unsupported hardware can remain in Overview without a distinct hardware-availability label.

**Change:** share device-specific names, geometry, glyphs, capabilities, and input aliases across every page. Give unfamiliar grip/paddle glyphs a readable name. Keep unsupported assignments available in a clearly marked section.

**Acceptance:** every visible control has the same identity in the overview, binding picker, tooltips, and diagram; focusing its row highlights the correct physical control. Test Steam Controller, Xbox, and PlayStation layouts separately. Keep the blue accent and use shape/text as well as color to convey state.

## Recommended implementation order

| Stage | Work | Exit check |
|---|---|---|
| 1. Make editing trustworthy | Findings 1–3: shared usage information, true discard, select newly created layer. | The three reproduced misleading workflows behave correctly with copied real profiles. |
| 2. Complete the layer workflow | Findings 4–6: composition, normal layer bindings, per-value inheritance and reset. | Apply Vehicles + hold Comms + edit/reset one value works predictably, including with hardware. |
| 3. Make complex profiles navigable | Findings 7–9: effect summaries, usage inspector, filters, compact layout, real Back history. | Find every use of a modifier and a truly spare input without manually scanning each editor. |
| 4. Finish controller presentation | Finding 10 and visual refinement of the earlier stages. | Accurate silhouettes/glyphs and consistent diagram highlighting across supported families. |

The main design rule should be **one input, one complete explanation of its behavior in the selected context**. Layers, conditions, activation, and inheritance should be reachable from that explanation. Preserve the fixed layer picker, grouped overview, action labels, and existing advanced disclosures.
